# _CreateIfercFixings

Built in #99; the index since #109; the examples newest first since #128; taken newest first since #147.

The IFERC fixings of one index: Inside FERC's index for each contract month whose index has been published, price beside code, as the desk keeps them, the newest month at the top, kept oldest first and reached by handle. Inside FERC, IFERC for short, prints one index per location per delivery month, around noon on the publication day its calendar sets for that month, the first business day of the month in most months and later around a holiday, January 2026's index having printed on the 5th, from the fixed-price deals of bidweek; the ICE basis and fixed-price futures on that location settle to it, the basis future to the index minus NYMEX's final settlement for the same month. The number here is Platts' index as printed, the fact the desk has; the subtraction is the instrument's arithmetic, and NYMEX's final settlement already lives in the NG futures fixings on its last trading day. The fixings are keyed by the month, not by the day the index appeared, because the [IFERC schedule](../index-definitions/iferc-schedule.md) holds that day beside each month's code, so the two need not say it twice. It replaced `_CreateMonthlyFixings`, which was dated by publication and checked against the futures schedule's publication column, and which nothing read; that creator, its page and its record went with #99. Since #105 the [market history](../market/market-history.md) reads them, binding each published month's index to its row of the IFERC calendar; before that only [util_ReadHandle](../utilities/read-handle.md) did. From #109 the creator takes the [index](../index-definitions/index.md), as the [futures fixings](futures-fixings.md) do since #108: it keeps the index by reference, so that the fixings say whose they are and the history can check that they and its calendar are one index's; it refuses an index of another kind; and it reads the index's schedule for its months, refusing a code that is none of them, the rule the history held since #105 moving to where the codes are typed and checked once. In #128 the [futures](futures-fixings.md) and [Gas Daily](gas-daily-fixings.md) fixings began taking their rows newest first, as the desk keeps a series; these fixings changed no rule then, a code carrying no date of its own, and the examples followed the desk while the months could still be typed in any order. From #147 the months are held to the same direction: the creator reads the day each month's index printed off the index's schedule, the publication day beside the code, requires each month to have printed before the month above, and keeps both columns the other way up, oldest first, the order the history reads, as the dated fixings do; `util_ReadHandle` turns them back, so a spill is the creator's own form, and the same months typed oldest first fail at their second row. The code is `src/goosedove/market_data/iferc_fixings.py`, the record and its builder, and `src/goosedove/excel/market_data.py`, the worksheet function.

## The library checks

Six rules, in this order, the first failure being the message. The first is the index's kind: the codes are checked against the months of an IFERC schedule, and only an IFERC index has one, so a futures or a Gas Daily index is refused naming its kind, as the calendar names kinds. The second comes with the columns: the price column has one row per code, since the seam never compares two columns and a series is rows. The third and fourth are read in one pass over the codes in row order, each row asked whether it names a month of the index and then whether it was given already, so the earliest offending row is named: each code is one of the index's months, matched exactly, spelling and case as typed, since an index for a month the schedule does not hold names nothing; and each code once, since a code given twice is two indices for one month and neither can be the month's. The fifth and sixth are read off the schedule, which holds the day each month's index printed beside its code, and are the order's, newest first since #147 as the dated fixings are since #128: a code the schedule holds at two rows names two days and is refused, in row order, naming the schedule's rows, while a month held twice that no code names is left to the [calendar](../calendar/calendar.md), whose rule it is; and each month printed before the month above's, one comparison over the column as the sheet gave it, which keeps the newest at the top and refuses two months printed on one day. The order is read from the publication days and from nothing else: not from a code's spelling, which runs the other way across a year's end, `F27` after `Z26`; not from the month's row in the schedule, which a calendar holds in order and a fixing does not read; and not from the day the future stopped trading. Rows count as the sheet counts them, the first row of the column being row 1, and within a rule the first row from the top that breaks it is named; a rule earlier in the order is reported before a later one, whichever row each is on, so a code given twice low in the column is reported before the order at its second row.

| Rule | Message |
|---|---|
| the index is an IFERC index, whose months the codes are checked against | `index is a futures index, expected an IFERC index` |
| the price column has one row per code | `price has 3 prices, expected 4, one per contract_code` |
| each code one of the index's months, spelling and case as typed | `contract_code row 2 is 'K26', expected one of the index's months` |
| each code once | `contract_code row 3 is 'G26', already given at row 2` |
| each code a month the index's schedule holds once | `contract_code row 1 is 'G26', a month the index's schedule holds at rows 2 and 3, expected a month it holds once` |
| each month published before the month above's | `contract_code row 2 is 'G26', published 2026-02-02, expected a month published before row 1's 'F26', published 2026-01-05` |

A count of one reads `1 price`, and a month held at three rows names all three, `at rows 2, 3 and 5`. Nothing else is checked. The codes are kept as typed, `f26` being no month of a schedule that spells it `F26`, and both columns are kept the other way up, oldest first, the codes as a tuple of the fixings' own and the prices copied once and frozen, each price beside its own code, so that a later change to the input cells changes no fixings; the index is kept by reference, the one the desk paired the series with. Nothing is sorted or filled: a series pasted oldest first, as any series could be before #147, fails at its second row, and the desk turns it over, because nothing in the library sorts anything and one direction is the only one taken; a month may still be left out, since whether a month's index has printed by a given day and whether every published month has its index are the history's rules, checked against the calendar it takes, and the history finds each index's row by its code as it did, now reading columns that already run its way. A single month is a series either way up, and the library's own callers make the fixings of no months. A failed call publishes nothing, and a column the seam rejects never reaches the function.

## Not here

Reading the fixings against a calendar: the [market history](../market/market-history.md)'s since #105, which takes the IFERC calendar and these fixings, from #109 requires the two to be one index's, the same index object and not merely the same name, and requires that every month published before the valuation date has its index and no other month has one, each index landing on its month's row, found by its code; that every code is a month of the index is checked here from #109, once, where the codes are typed, and the order of the months from #147. The day an index printed: the [IFERC schedule](../index-definitions/iferc-schedule.md)'s, beside the month, read here for the order and kept nowhere but there. A schedule that holds a month at two rows, or whose publication days do not increase: the [calendar](../calendar/calendar.md)'s to refuse, as before; the fixings refuse a code that names a month held twice and read the days of the months they are given, no others. NYMEX's final settlement for the month and the basis future's settlement, index minus that settlement: the instrument's, with the NG futures fixings beside it. A revised index: a new fixings object, never an edit; the library tells a provisional value from a published one in no way, a value supplied being a value. The monthly fixings of #76 and #81: removed in #99, their page with them; the futures schedule's publication column, which they alone read, went in #102. A holiday calendar: an IFERC index has none. Sorting a series and filling a missing month: nothing here, the desk turning a series over and pasting a month, as for the dated fixings since #128. A reader of its own: [util_ReadHandle](../utilities/read-handle.md) spills any fixings as two columns. Pricing and risk.
